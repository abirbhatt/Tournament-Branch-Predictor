Part 0, continuedThe interface and the timing contract

All three predictors share one interface. Getting the timing contract right up front prevents the most confusing class of bugs.

PortDirMeaning
pred_pc[31:0]inPC of the branch being predicted this cycle
pred_validin1 when a predict is happening this cycle. Only matters for speculative history (Part 5).
pred_takenoutThe prediction. Combinational: the testbench samples it in the same cycle. No flops on this path.
pred_meta[63:0]outAny state you'll need at update time. The testbench stores it with the branch and hands it back on upd_meta.
upd_validinA branch is resolving this cycle. Commit your updates on this posedge.
upd_pc, upd_takeninThe resolving branch and its actual outcome
upd_mispredin1 if this branch was predicted wrong (provided for convenience)
upd_meta[63:0]inThe pred_meta your design produced when this branch was predicted
rstinSynchronous, active-high. Clears the GHR only, never the tables.
Exact spec: timing contract
  • The predict read sees state before the clock edge. Update writes happen at the edge.
  • If a predict and an update touch the same entry in the same cycle, the predict sees the old value. A combinational (asynchronous) read plus a clocked write gives you this automatically.
  • Serial mode (--lat 1 --depth 1, the default) never predicts and updates in the same cycle. Part 5's pipelined mode does.
Concept: what pred_meta really is

In a real core, the prediction is made at fetch, but the outcome is known only at execute, many cycles later. Any predictor state needed at update time (which counter was used, what the history looked like) travels down the pipeline with the branch. This is often called the branch's predictor metadata or history snapshot.

pred_meta is that metadata. The testbench plays the role of the pipeline: it carries your 64 bits alongside the branch and returns them at resolve. You decide the contents and bit layout. Use only what you need, and zero-fill the rest.

Part 1Bimodal predictor

The simplest useful dynamic predictor: one small counter per branch that remembers which way it usually goes. Everything else in this lab is built on it.

Concept: the 2-bit saturating counter

A 2-bit saturating counter has four states. Predict taken when the MSB is 1. On each resolved branch, step toward the actual outcome: increment if taken, decrement if not, and saturate (stop) at 0 and 3.

The key property is hysteresis: from a "strong" state it takes two wrong outcomes in a row to flip the prediction. One surprise doesn't erase what the counter learned.

Worked example: why two bits beat one

A loop branch that runs 3 iterations then exits produces the pattern T T T N, repeating. Follow one counter starting at 01:

Outcome #12345678
Counter before0110111110111111
PredictionNTTTTTTT
ActualTTTNTTTN
Resultmisshithitmisshithithitmiss

After warm-up, it misses once per loop exit. The exit only drops the counter to 10, which still predicts taken for the next loop entry. A 1-bit counter would flip to N on the exit and then also miss the first iteration of the next loop: two misses per loop.

Concept: bimodal = a table of counters indexed by PC

A bimodal predictor is a table of 2N counters. The low bits of the branch PC pick the entry. Instructions are 4-byte aligned, so pc[1:0] is always 00 and carries no information; the index starts at bit 2.

Concept: aliasing

Different branches whose PCs share the same index bits land on the same counter. This is aliasing. When the two branches behave oppositely, they fight over the counter (destructive aliasing) and both mispredict more. Bigger tables reduce aliasing, until every static branch has its own entry; after that, more entries buy nothing.

Exact spec: bimodal
  • Table: 2BIM_BITS 2-bit counters.
  • Index = pc[BIM_BITS+1:2].
  • Every counter is 2'b01 at time 0 (an initial block). rst does not touch the table.
  • pred_taken = MSB of the indexed counter, combinationally.
  • On posedge clk with upd_valid: saturating increment if upd_taken, else saturating decrement.
Your task
  1. Declare the table as a memory array of 2-bit regs, with depth derived from the parameter (see the Verilog toolbox at the back).
  2. Initialize it in an initial block with a for loop. This is legal for simulation and for FPGA RAM initialization, which matters in Part 6.
  3. Predict: slice the index out of pred_pc and drive pred_taken from the counter's MSB with a continuous assign.
  4. Update: write the saturating counter logic in an always @(posedge clk) block with nonblocking assignments. Decide: does bimodal need pred_meta at all, or is upd_pc enough?
  5. Consider putting the saturating update in a small function. You'll need it three more times.
Checkpoint
python3 run.py --pred bimodal --trace all

All seven traces show [PASS]. Also try --bim-bits 6 and --bim-bits 14; a design that only works at the default size has a hard-coded width somewhere.

Pitfalls
  • Wrap-around instead of saturation: 2'b11 + 1 is 2'b00 in 2-bit arithmetic. Check the bounds explicitly.
  • Off-by-one slice: pc[BIM_BITS+1:2] is BIM_BITS bits wide. pc[BIM_BITS:1] compiles fine and is wrong.
  • pred_taken is X/Z: uninitialized table, or the index width doesn't match the table depth.
  • Mismatch on the first branch usually means a wrong index or init value. A mismatch after a few dozen usually means saturation logic.
Think about
  1. Why start counters at weakly not-taken instead of strongly not-taken?
  2. Bimodal is weak on interp. Why can't a bigger table fix that?
  3. In the Part 4 sweep, bimodal's accuracy stops improving past a certain size. Predict where, for cfg_large, before you run it.

Part 2Gshare

Bimodal knows which branch it's looking at. Gshare also knows how we got here: the outcomes of the last few branches. That lets it predict branches whose behavior depends on context.

Concept: global history and correlation

The global history register (GHR) is a shift register holding the outcomes of the most recent branches, any branches, not just this one. Bit 0 is the most recent.

Many branches are correlated with earlier ones. In the interp workload, which dispatch check succeeds depends on which opcode comes next, and the recent sequence of dispatch outcomes identifies where you are in the program. A per-PC counter sees a confusing mix; a counter chosen by (PC, history) sees a consistent pattern.

Gshare forms the table index as PC XOR GHR. The same branch now uses different counters in different history contexts.

Same branch, different histories, different counters

pc[5:2]GHR (recent outcomes)Index = pc ⊕ GHR
010100110110 (entry 6)
010110101111 (entry 15)
010101010000 (entry 0)

That's the strength and the cost: one static branch can now occupy many entries, so gshare needs more capacity and more warm-up than bimodal, and XOR collisions create new aliasing between unrelated (PC, history) pairs.

Exact spec: gshare
  • GHR is GSH_BITS wide, cleared to 0 by rst. Bit 0 = most recent outcome.
  • Predict index = pred_pc[GSH_BITS+1:2] ^ GHR. Counters start at 2'b01.
  • Non-speculative history: on upd_valid, shift the GHR left by one and insert upd_taken at bit 0.
  • Update the counter you predicted from. Use the index computed at predict time, carried in pred_meta. Don't recompute it from the current GHR at update time.
Concept: why the predict-time index?

In serial mode, the GHR doesn't change between predict and update, so recomputing would happen to give the same answer. In Part 5, other branches resolve in between and the GHR moves on. The counter that made this prediction is the one that should learn from its outcome. Getting this right now saves you a confusing bug later.

Your task
  1. Add the GHR register with its synchronous reset.
  2. Compute the predict index, drive pred_taken, and pack the index into pred_meta (zero-extend to 64 bits).
  3. On update, unpack the index from upd_meta, update that counter, and shift the GHR.
Checkpoint
python3 run.py --pred gshare --trace all
python3 run.py --pred gshare --gsh-bits 13 --trace interp,cfg_large
Pitfalls
  • Shift direction: newest outcome enters at bit 0 and everything moves up. A right shift compiles and fails around branch #2.
  • Using blocking = in the clocked block for the GHR and counter together can make the counter update use the new GHR.
  • Forgetting the GHR reset leaves it X, which makes every index X.
Think about
  1. Gshare beats bimodal on interp but loses on several other traces. Why?
  2. For a fixed table size, what happens as history gets longer?
  3. Why does gshare need more warm-up than bimodal?

Part 3Tournament predictor

Bimodal and gshare are good at different branches. A tournament predictor runs both and learns, per branch, which one to trust.

Concept: hybrid prediction

A tournament (or hybrid) predictor runs bimodal and gshare in parallel. A third table, the chooser (or meta-predictor), holds 2-bit counters indexed by PC. Chooser MSB = 1 means "trust gshare for this branch." This is the idea behind the Alpha 21264's predictor.

The chooser learns only from branches where the two components disagreed, because only those tell you which component is better.

Chooser update rule

Bimodal saidGshare saidActualChooser action
TTeitherno change (they agreed, so there's nothing to learn)
NNeitherno change
NTT+1 (toward gshare: gshare was right)
NTN−1 (toward bimodal)
TNT−1 (toward bimodal: bimodal was right)
TNN+1 (toward gshare)

"Bimodal said" and "gshare said" mean their predictions at predict time. By update time the counters may have changed.

Exact spec: tournament (SPEC_HIST = 0)
  • Three tables, all counters 2'b01 at time 0: bimodal (index pc[BIM_BITS+1:2]), gshare (index pc[GSH_BITS+1:2] ^ GHR), chooser (index pc[CHO_BITS+1:2]).
  • pred_taken = chooser MSB ? gshare prediction : bimodal prediction.
  • On update: update both component counters toward the outcome (gshare at its predict-time index). Update the chooser only if the components disagreed at predict time, per the table above.
  • GHR: non-speculative, exactly as in Part 2.
  • Add the SPEC_HIST parameter now, but leave it unused until Part 5.

Design worksheet: lay out your metadata before you write code

Your task
  1. Fill in the worksheet. List everything the update step needs that it can't recompute correctly later. (Hint: there are three things, and one of them is a whole register.)
  2. Decide on structure: instantiate your Part 1/2 modules, or write the three tables directly in one module. Both work. The single-module version is easier to synthesize and to reason about in Part 5.
  3. Write the three parallel reads and the selection mux.
  4. Write the update: both components, then the chooser with its disagreement condition, then the GHR.
Checkpoint
python3 run.py --pred tournament --trace all
python3 run.py --pred tournament --bim-bits 8 --gsh-bits 12 --cho-bits 9 --trace all

The second command uses asymmetric sizes, which catch slicing bugs that symmetric sizes hide (for example, using BIM_BITS where you meant CHO_BITS).

Pitfalls
  • Re-reading the component counters at update time to decide the chooser update. It passes serially and fails in Part 5.
  • Inverted chooser polarity (MSB = 1 meaning bimodal). Pick the spec's convention.
  • Meta field overlap: with asymmetric sizes, fixed bit offsets can collide. Derive offsets from the parameters.
Think about
  1. Why update the chooser only on disagreement?
  2. Why must the chooser use the predict-time component predictions?
  3. With a fixed total budget, how would you split it across the three tables? How could you test your idea with run.py?

Part 4Capacity sweep

A microarchitect's real question is never "does it work?" but "how big should it be?" Here you answer that with data from your own RTL.

Your task
python3 sweep.py capacity --limit 20000   # quick first look (~1/5 the time)
python3 sweep.py capacity                 # final numbers

This runs about 100 RTL simulations, each one checked against the golden model, across bimodal, gshare, and tournament at five sizes each. It writes:

  • results/capacity.png: mean accuracy vs. storage (KiB, log scale)
  • results/summary_capacity.md: the full table, including per-trace accuracy
  • results/capacity.csv: raw data

Use --jobs N to set parallelism. If any run fails the golden check, the script says so, and you shouldn't use those numbers.

Concept: how to read the plot
  • A plateau means the structure has stopped being capacity-limited. More storage buys nothing because the remaining mispredictions come from something else (unpredictable data, or missing information like history).
  • The gap between curves at equal storage is the value of a better algorithm, holding area fixed. That's the comparison that matters in a design review.
  • The per-trace columns tell you where an advantage comes from. A mean can hide that one workload drives the entire difference.
  • The knee of a curve is usually the sweet spot: past it, each doubling of area buys less and less.

Analysis to write (3–5 sentences, for your README)

  1. Where does each predictor plateau, and why? Tie it to the workloads.
  2. Which traces drive the tournament's advantage over the best single component?
  3. At roughly 0.75 KiB, how much better is the tournament than the best single predictor of similar size?
  4. Pick a size you'd ship and justify it like a design review: accuracy gained vs. area spent.
Think about
  1. Does anything in the table surprise you, like a bigger configuration doing slightly worse? What could cause that?
  2. Accuracy is a proxy. What does a real team care about instead, and what information would you need to compute it? (Hint: think in mispredicts per instruction, and what a mispredict costs in cycles.)

Part 5Pipelined updates and speculative history

So far, each branch resolved before the next one was predicted. Real cores don't work that way. This part models what actually happens, shows the damage it does to gshare, and has you fix it the way real front-ends do.

Concept: the stale-history problem

A core predicts at fetch but only learns the outcome at execute, many cycles later. Meanwhile it keeps fetching and predicting younger branches. With non-speculative history, the GHR only updates at resolve, so those younger branches are predicted with a GHR that's missing every branch still in flight. Gshare's whole advantage is knowing recent history, and that's exactly what it loses.

The testbench's pipeline model

Run with --lat L --depth D: up to D branches can be in flight, each resolving L cycles after it was predicted. On a mispredict, every younger in-flight branch is squashed (its update never happens) and fetch rewinds to the branch right after the mispredicted one. That's the trace-driven version of a pipeline flush.

Step 1: see the problem (no new code)
python3 run.py --pred tournament --trace all
python3 run.py --pred tournament --lat 16 --depth 32 --trace all

Both should pass (the golden model has the same non-speculative behavior). Compare accuracy per trace. Which workload is hurt most, and why that one? Write your answer down before moving on.

Concept: speculative history with checkpoint repair

Fix: update the GHR at predict time with the predicted direction. Younger branches now see history that includes every older in-flight branch, assuming the predictions were right.

When a prediction turns out wrong, the GHR contains a wrong bit (and everything after it is wrong-path history). Repair it: restore the GHR the mispredicted branch saw at predict time (your checkpoint, already in its metadata), then shift in the actual outcome. That's exactly the correct history, because every older branch has already resolved correctly.

Compare this to your Tomasulo core: there, you checkpointed the rename map at each branch and restored it on a mispredict. Same idea, different state.

Exact spec: SPEC_HIST = 1
  • On pred_valid: shift pred_taken into the GHR (at the clock edge ending the predict cycle).
  • On upd_valid && upd_mispred: GHR ← (predict-time GHR from upd_meta) shifted left, with upd_taken at bit 0.
  • On a correctly predicted update: don't touch the GHR. It already holds the right bit.
  • If a repair and a predict happen in the same cycle, repair wins. (The testbench never predicts in a flush cycle, but define it anyway.)
  • The tables and chooser update exactly as in Part 3, non-speculatively at resolve.

Worked example: 4-bit GHR, LAT = 3, same branches as Figure 5.1

CycleEventcheckpoint (meta)spec GHR after edgenon-spec GHR seen at predict
c0predict b0 → T000000010000
c1predict b1 → N000100100000
c2predict b2 → T001001010000
c3b0 resolves T ✓ · predict b3 → T010110110000
c4b1 resolves N ✓ · predict b4 → N101101100001
c5b2 resolves N ✗ · squash b3, b4—0100 (repair: 0010 → 0100)—
c6predict b3 again0100…0100

Three things to notice:

  • In c3, b3 is predicted with non-spec history 0000 even though three older branches (T, N, T) have already been predicted. Speculative history gives it 0101. That's the information gshare was missing.
  • b3 and b4 were predicted with history that included b2's wrong bit. That doesn't matter: they're squashed and refetched. Only the oldest mispredicted branch ever needs to repair.
  • The repaired value 0100 is exactly the true history: b0 = T, b1 = N, b2 = N.
Step 2: implement it
  1. Your pred_meta should already carry the predict-time GHR. Confirm it does. That's your checkpoint.
  2. Rewrite the GHR's next-state logic as a priority choice between three cases: repair, speculative shift, hold. Keep the Part 3 behavior under SPEC_HIST = 0; since it's a parameter, a plain if on it is constant-folded by synthesis.
  3. Leave the table and chooser updates alone.
Checkpoint
python3 run.py --pred tournament --spec-hist 1 --trace all
python3 run.py --pred tournament --spec-hist 1 --lat 16 --depth 32 --trace all
python3 sweep.py latency --size 10

The first command must give identical accuracy to non-spec in serial mode. Make sure you understand why. The sweep writes results/latency.png: accuracy vs. resolve latency for both history modes.

Think about (the part interviewers dig into)
  1. Walk through why the repaired GHR is exactly correct, with 5 younger branches in flight.
  2. Why don't the younger branches need their own repair?
  3. Why does serial mode give identical results with and without speculation?
  4. What did speculation do to your critical path, and how might a real design break that loop?
  5. A return address stack is also updated speculatively at fetch. What would its checkpoint and repair look like?
  6. Why are the counter tables still updated non-speculatively at resolve, even though the GHR is speculative?

Part 6Synthesis and PPA

An accuracy number alone doesn't make a design. Microarchitects trade accuracy against area, timing, and power. Here you get real numbers from Vivado.

Your task
# from bp_lab/;  args: index bits, SPEC_HIST, clock period (ns)

vivado -mode batch -nojournal -nolog -source synth/synth.tcl -tclargs 10 1 4.0

The script runs out-of-context synthesis and place-and-route for the Nexys A7-100T part (xc7a100tcsg324-1). It constrains the I/O ports so the combinational predict path is actually timed instead of ignored, and prints one SUMMARY line with LUTs, LUTRAM, FFs, BRAM, WNS, and Fmax. Full reports land in results/.

I wrote this script without a Vivado install to test against. If a command errors, fix it or run the same steps in the GUI; the reports are what matter.

Concept: LUTRAM vs. block RAM

FPGAs offer two kinds of RAM. Distributed RAM (LUTRAM) is built from LUTs and supports an asynchronous read: address in, data out, same cycle. Block RAM (BRAM) is denser but has a synchronous read: the address is registered, and data comes out a cycle later.

Your predict port must answer in the same cycle, so your tables should map to LUTRAM. If you see thousands of flip-flops instead, something blocked RAM inference (the usual culprit is resetting the tables in the rst branch).

What to look at

  • Mapping: did all three tables become LUTRAM? Roughly how many LUTs per KiB?
  • Worst path: open results/synth_*_timing.rpt. Is it the predict path or the update path? Does it match Figure 5.2?
  • Spec vs. non-spec: compare WNS and Fmax at 10 bits. Is the difference what you predicted?
  • Scaling: 10 → 12 bits is 4× the storage. How do area and Fmax respond? Why isn't timing hurt as much as area?
Think about
  1. Using BRAM would make this a 2-cycle predictor. How do real front-ends predict every cycle anyway?
  2. On an ASIC, these tables would be SRAM macros instead of LUTRAM. What changes about the area and timing trade-off?

ReferenceVerilog toolbox

Generic syntax patterns you'll need. These use made-up names on purpose: they show how to write a construct, not your design.

Parameter-sized memory array

localparam DEPTH = 1 << ADDR_BITS;           // 2^ADDR_BITS entries
reg [WIDTH-1:0] mem [0:DEPTH-1];            // DEPTH entries, WIDTH bits each

Initialize a memory at time 0

integer k;
initial begin
  for (k = 0; k < DEPTH; k = k + 1)
    mem[k] = SOME_INIT_VALUE;
end

Synthesis tools treat this as the RAM's power-on contents. Putting the same loop under if (rst) instead would turn the RAM into thousands of flip-flops.

Asynchronous read, synchronous write

assign rdata = mem[raddr];                   // combinational read
always @(posedge clk)
  if (we) mem[waddr] <= wdata;               // clocked write, nonblocking

Part-select with a parameter, and zero-extension

wire [ADDR_BITS-1:0] a = some_bus[ADDR_BITS+OFFSET-1:OFFSET];
assign wide_out = {{(64-W){1'b0}}, narrow_value};       // zero-extend W bits to 64
wire [W-1:0] field = wide_in[LSB+W-1:LSB];              // unpack a field

Shift register with a new bit entering at the bottom

always @(posedge clk)
  if (rst)        sr <= {W{1'b0}};
  else if (shift) sr <= {sr[W-2:0], new_bit};

A function

function [1:0] my_func;
  input [1:0] x;
  input       flag;
  begin
    my_func = ...;     // combinational logic only; no delays, no clocks

Debug order when something fails

  2. First mismatch report: compare your index, then your counter value, then your output against the golden state.
  3. Shrink it: --limit 50 and a single trace.
  4. Waveform: --vcd, jump to the cyc= from the report.
  5. Read the spec in code: model/golden.py is short. When in doubt, it's the truth.

AppendixAnswers to the Think-about questions

Try each one yourself first. Saying an answer out loud before you read it is the best interview practice you can do.

Part 1: Bimodal

1. Why weakly not-taken?

A weak initial state means one outcome is enough to learn a branch's direction; a strong state would need two. The direction is a judgment call: many designs start weakly taken, because most branches (especially loops) are taken. What matters is that it's weak.

2. Why can't a bigger table fix interp?

The dispatch branches don't have a fixed bias: whether a check succeeds depends on the opcode, which changes every pass. A per-PC counter sees a mixed sequence and can only predict the majority. The information needed is in the recent history, not the PC. More entries just give each branch its own counter, which it already has.

3. Where does bimodal plateau?

Once every static branch has its own counter, there's no aliasing left to remove. cfg_large has 512 static branches at consecutive addresses, so it stops improving at 9 index bits (512 entries). The small workloads have a handful of branches and plateau almost immediately.

Part 2: Gshare

1. Why does gshare lose on some traces?

Each static branch is spread across many entries, one per history pattern it appears with. For branches whose behavior doesn't depend on history, that's pure cost: more capacity used, more aliasing with other (PC, history) pairs, and more warm-up. Unpredictable branches in the history also scramble the index, splitting one context into many.

2. Longer history, fixed table?

More distinct contexts compete for the same entries, so aliasing rises and each context trains more slowly. Longer history only pays off if correlation really reaches that far back and you have the capacity to hold the extra contexts. That tension is what modern predictors like TAGE solve, by using several tables with different history lengths.

3. Why more warm-up?

Each (PC, history) context is a separate counter that has to be trained on its own. A branch seen with 16 different histories needs about 16 times as many visits before all its counters are warm.

Part 3: Tournament

1. Why update the chooser only on disagreement?

When both components agree, the chooser's choice didn't affect the prediction, and the outcome tells you nothing about which component is better. Updating on agreement would push the chooser around based on noise.

2. Why predict-time component predictions?

The chooser should judge the predictions that were actually made. In a pipelined design, the component counters may have been updated by other branches between predict and resolve, so re-reading them gives you a different question's answer.

3. Splitting the budget

Gshare usually deserves the largest table, because it needs capacity for many contexts per branch. Bimodal and the chooser are PC-indexed and saturate once each static branch has an entry. You can test this directly: hold the total roughly fixed and run run.py with different --bim-bits / --gsh-bits / --cho-bits.

Part 4: Capacity

1. Bigger doing slightly worse?

Possible causes: longer history (gshare's history length grows with its index bits here) adds contexts that need more warm-up than the trace provides; or a different aliasing pattern happens to hurt one workload. Small differences can also just be noise in a 100K-branch trace.

2. What teams care about instead of accuracy

MPKI (mispredicts per 1000 instructions) times the mispredict penalty in cycles gives lost cycles, which maps to IPC. You'd need instruction counts between branches and the pipeline's flush penalty, which is why real studies use full-program traces.

Part 5: Speculative history

1. Why is the repaired GHR exactly correct?

Branches resolve in order. When branch k resolves as mispredicted, every older branch has already resolved correctly, so its predicted bits in the history were right. Branch k's checkpoint holds exactly that older history. Shifting in k's actual outcome gives the true history through k. All five younger branches are squashed, so nothing after k belongs in the GHR anymore.

2. Why don't younger branches repair?

They were on the wrong path. They're squashed before they resolve and are refetched after the repair, at which point they're predicted with correct history.

3. Why is serial mode identical?

With one branch in flight, nothing is predicted between a branch's predict and its resolve. The speculative shift either turns out right (so the GHR matches what non-spec would compute at resolve) or is repaired to exactly that value. Either way, the next branch sees the same GHR in both modes.

4. Critical path

The GHR's next state now depends on pred_taken, so index, table read, and mux all happen in the same cycle as the GHR write. Real designs break this by pipelining the predictor over two or more cycles, updating the history a cycle later, or using ahead pipelining (starting the lookup with older history and resolving the last bits late).

5. Return address stack

Checkpoint the top-of-stack pointer (and often the top entry, since a wrong-path push can overwrite it) with each branch. On a mispredict, restore them. Same pattern: small state, cheap to snapshot, restored by the oldest mispredict.

6. Why non-speculative table updates?

Updating counters with wrong-path outcomes would pollute them, and the tables are far too large to checkpoint. The GHR is a few bits, so checkpointing it is cheap. That asymmetry (speculate on small state, commit big state at resolve) shows up all over CPU design.

Part 6: PPA

1. Predicting every cycle with a slow predictor

Overriding predictors: a small, fast predictor gives a same-cycle guess, and the larger, slower one overrides it a cycle or two later, re-steering fetch if they disagree. Also ahead pipelining, which starts the lookup for a future branch before its PC is final.

2. ASIC SRAM vs. LUTRAM

SRAM macros are much denser than flops or LUTs, so area per bit drops, but their access time and fixed read latency often dominate timing. Port count matters too: a predictor that reads and writes in the same cycle needs a 2-port array or banking. Those constraints are part of why real predictors are pipelined.
